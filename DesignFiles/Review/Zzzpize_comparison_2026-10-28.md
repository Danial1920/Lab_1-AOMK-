| AssemblyFiles внутри каждого компонента | Отдельная сборка компонента; клиент связывается с библиотеками |

В SourceFiles находятся реализация и фабрика; HeaderFiles описывают внутреннее состояние; SharedFiles — публичные интерфейсы и идентификаторы. Лабораторные на одной ветке; версия ЛР1 отмечена тегом.

Схема образца:

```text
Lab2
  агрегирует Lab1
    агрегирует B -> клиент получает X самого B
    включает E (резерв D) -> собственный фасад Y
  включает A -> Addition в Horner
  включает D -> Multiplication в Horner
C подставляется вместо A в отдельной сборке при неизменных CID и коде Lab2.
```

Наша схема:

```text
Lab2
  агрегирует Lab1
    включает C -> собственные фасады X/Y
      включает A -> Addition
      включает D -> Y и Subtraction через X
        включает B -> X
  включает E -> собственный фасад Y
    агрегирует B -> X компонента E
```

В нашей схеме есть агрегация Lab2→Lab1 и E→B, но нет последовательной агрегации Lab2→Lab1→B. Наш публичный X в Lab2 принадлежит фасаду Lab1, а не B.

## Расхождения по важности

### 1. Высокий приоритет: несовместимый контракт клиент–сервер

Образец использует X `93221116-2248-4742-AE06-82819447843D` и Y `BD6414C2-9096-423E-A90C-04D77AFD1CAD`. Аргументы — int16; Addition/Multiplication возвращают int32, Subtraction/Division — int16. В Y пять методов с учетом Unknown.

У нас в `SharedFiles/IEcoCalculatorX.h:6` и `SharedFiles/IEcoCalculatorY.h:6` другие IID; аргументы/результаты double, в Y добавлен TryDivision. Например, 20/3 означает 6 в образце и дробное значение у нас.

Клиент и сервер, собранные с нашими согласованными заголовками, работают. Но учебный клиент не запрашивает наши IID; готовые учебные A–E нельзя просто заменить нашими аналогами. Нельзя исправить это одной заменой UUID: сигнатуры и таблицы методов тоже должны соответствовать.

**Исправление для соответствия образцу:** предоставить стандартные X/Y с неизменными IID и сигнатурами. Существующий double-API, если сохранять, вынести под отдельные названия и IID. Безопасное деление со статусом оформить отдельным расширяющим интерфейсом. Численный polyfit не переводить в int16.

### 2. Высокий приоритет: C не демонстрирует заменяемость A

У образца A/C имеют одинаковый CID; `CALC_A=Eco.CalculatorC` выбирает другую библиотеку без изменения Lab2. У нас `SharedFiles/IdEcoLab2.h:10` и `:12` задают разные CID. Более того, наш C сам создает A (`SourceFiles/CalculatorComponents.c:228`). Если просто зарегистрировать C под CID A, получится рекурсивное создание C→A→C.

**Исправление:** сделать C самостоятельной расширенной реализацией контракта A. Добавить два запуска одного клиента: A и C под одним CID, в разных процессах/наборах библиотек. Не регистрировать две конфликтующие версии одновременно. Показать сохранение X и появление Y.

### 3. Средний приоритет: другая демонстрация агрегирования

`SourceFiles/CEcoLab1GeneratedFactory.c:454` включает C с NULL outer, а не агрегирует B. `SourceFiles/EcoLab2.c:130` агрегирует Lab1, после чего включает E. Это реальная композиция, но не сценарий образца с двумя уровнями агрегации X.

**Для воспроизведения образца:** Lab1 агрегирует B и включает E/D; Lab2 агрегирует Lab1. При создании B Lab1 передает свой controlling unknown, который при внешней агрегации принадлежит Lab2. NDQI Lab1 возвращает X через private unknown B. Клиент проверяет X→Unknown==Unknown(Lab2), X→Lab2 и продолжение работы после освобождения исходной ссылки Lab2.

Это рекомендация соответствия выбранному образцу, а не утверждение, что PDF запрещает нашу топологию.

### 4. Средний приоритет: нет законченного вычисления Lab2 через включенные компоненты

В образце Horner вызывает A.Addition и D.Multiplication; клиент сравнивает результат с независимым вычислением. Наш `SharedFiles/IEcoLab2.h` содержит только QI/AddRef/Release. Вызовы Y действительно доходят до включенного E, а polyfit доступен через агрегированный Lab1, поэтому Lab2 не является пустым объектом. Но собственного прикладного метода, связывающего несколько включенных компонентов, нет.

**Для наглядной защиты:** добавить вычисление полинома через включенные X/Y и показать маршрут вызовов. Horner уместен для задания polyfit, однако не следует подменять им сам метод МНК. Само наличие Horner не является прямым требованием PDF.

### 5. Средний приоритет: независимость демонстрационного клиента и комплект поставки

У нас обычная цель `eco-build` компилирует серверные C вместе с тестом; это не фейк, но такой запуск не проверяет комплект отдельных статических библиотек. A–E реализованы общей структурой и ветвлением kind; по отдельным CID создаются разные объекты и фабрики. Dynamic-скрипт собирает отдельные dylib, однако вся экспортная развилка находится в фабрике Lab1.

**Улучшение:** отдельные сборочные цели/артефакты A–E/Lab1/Lab2, клиент только с публичными заголовками и библиотеками; понятный демонстрационный вывод по каждому сценарию. Разнос исходников по каталогам облегчает проверку, но сам по себе не делает компонент корректным. Существующие строгие регрессионные тесты сохранить.

## Что подтверждено в нашем сервере и клиенте

- Eco-клиент получает реальные объекты через QueryComponent, а не подставляет заранее вычисленные ответы.
- Агрегируемые фабрики принимают outer только при запросе Unknown. Отдельный private unknown управляет внутренним временем жизни; публичные QI/AddRef/Release делегируют контроллеру.
- Матрица поддерживаемых интерфейсов и общий Unknown проверяются для восьми CID. Проверяются удержанные интерфейсы после освобождения исходной ссылки, неизвестный IID, NULL и ошибки выделения памяти.
- Lab1/Lab2 владеют полученными системными интерфейсами. Калькуляторы не сохраняют системный интерфейс для последующей работы; владеют allocator и дочерними ссылками.
- Интеграционный allocator инструментируется: успешные операции передаются исходной реализации, выбранное выделение намеренно возвращает NULL. Это тестовое внедрение отказа, а не подмена шины/фабрики/результата QI.
- Проверка ошибочной арифметики подтверждена мутацией настоящего компонента в временной копии. Успешный итог не печатается независимо от состояния проверок.
- Положительный путь `EcoLab2_RegisterOnBus` дополнительно выполнен нашим независимым клиентом совместимости. Rollback-ветви helper-регистрации этим запуском не проверены.

## Что не следует копировать автоматически

В C и D образца QI(Unknown) через X возвращает адрес таблицы X, а через Y — адрес таблицы Y. Это нарушает каноническую identity для самостоятельного объекта; штатные 20 тестов клиента Lab2 не проверяют этот конкретный случай. Вывод сделан по исходникам, отдельный отрицательный запуск этого случая здесь не выполнялся.

Фабрики Lab1/Lab2 также перезаписывают результат Init результатом QI; ошибки создания детей могут маскироваться. Успешные штатные тесты не доказывают корректность этих ошибочных путей. Наш fail-fast и проверки identity нужно сохранить при переносе учебной схемы.

## Рекомендуемый порядок исправления

1. Стандартные X/Y и независимый клиент, который успешно использует их; прежние double-возможности при необходимости оставить отдельным расширением.
2. Стандартные роли A/B/C/D/E; две сборки A/C под одним CID.
3. Lab1: агрегированный B, включенный E/D; Lab2: агрегированный Lab1. Проверить двухуровневый controlling unknown.
4. Полезный метод Lab2 через включенные A/D и отдельная понятная демонстрация.
5. Самостоятельные артефакты компонентов и клиент без серверных исходников; затем регрессии, Dynamic, документация и отчет по фактической новой схеме.

Ни количество проверок, ни сходство каталогов, ни оценка чужой работы не гарантируют оценку нашей. Главный проверяемый результат исправления — работа независимого клиента с учебными контрактами и явная демонстрация каждого требуемого механизма.
